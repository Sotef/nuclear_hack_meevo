**Сек постпроцесса на 1 мин аудио (GPU, оценка по сегментам).**

- `full`: ~650 ток/мин / 22.15 ток/с ≈ **29 с/мин** (с учётом JSON-обвязки).

Это скорость GPU-стенда, не телефона.

## 4. Оценка для мобилы (аналитика, не замер)

Все цифры ниже — **оценка**, не измерение на устройстве. Телефон среднего
класса, Android arm64-v8a, LPDDR4X/LPDDR5 ~25–51 ГБ/с, big-cores с
NEON/dotprod, ONNX Runtime Mobile/GenAI.

### 4.1 LLM: веса, KV-кэш, пик RAM

- Веса int4: **1.108 ГБ** (измерено по файлам `model.onnx` + `model.onnx.data`).
- KV-кэш: 28 слоёв × 2 (K/V) × 8 KV-heads × 128 head_dim × 2 байта (fp16)
  = **0.1147 МБ/токен**.
  - контекст 256 токенов → 29.4 МБ;
  - 512 → 58.7 МБ;
  - 1024 → 117.4 МБ.
- Рабочие буферы/активации/токенизатор: ~100–200 МБ (оценка).
- **Пик RAM LLM ≈ 1.108 + KV + 0.15 ≈ 1.29–1.38 ГБ** (контекст 256–1024).
  Для запаса: **1.3–1.5 ГБ**.

### 4.2 LLM: скорость декода (bandwidth-bound)

Декод авторегрессии читает все веса на каждый токен, поэтому ограничен
пропускной способностью памяти:

```
tok/s ≈ (BW_effective) / (размер весов)
BW_effective = BW_peak × КПД (0.6–0.75)
```

- 25 ГБ/с × 0.6 / 1.108 ГБ ≈ **13.5 ток/с**;
- 51 ГБ/с × 0.75 / 1.108 ГБ ≈ **34.5 ток/с**.

С поправкой на мобильный контроллер памяти и неполную загрузку big-cores
принимаем рабочий диапазон **10–25 ток/с**, среднее **~15 ток/с**.
Prefill (compute-bound) — **50–150 ток/с**, среднее ~100 ток/с.

### 4.3 LLM: сек/предложение и сек на 1 мин аудио

Средние токены на сегмент (из GPU-прогона): prompt 83.9, generated 22.7.

```
t_сегмент = prompt_tokens / prefill_tok_s + generated_tokens / decode_tok_s
```

| Сценарий | Decode 10 ток/с, prefill 50 | Среднее (15 / 100) | Decode 25, prefill 150 |
|---|---:|---:|---:|
| `punctuate`, с/сегмент | 3.95 | **2.35** | 1.47 |
| `punctuate`, с/мин (16.2 сегм.) | 64.1 | **38.2** | 23.8 |
| `correct`, с/мин (оценка) | 30–40 | **25–30** | 15–20 |
| `full`, с/мин (оценка) | 70–85 | **50–60** | 35–45 |

Итог для продукта: **LLM-постпроцесс на телефоне ≈ 38 с на 1 мин аудио**
для `punctuate` (диапазон 24–64 с), **50–60 с/мин** для `full`.
Это делает LLM самым тяжёлым звеном пайплайна; для real-time нужен
батчинг/сокращение числа сегментов или модель меньше 1B.

### 4.4 ASR на телефоне

Desktop baseline: small zipformer-ru int8, 1 thread CPU, RTF **0.018949**
(`tools/eval_asr/hyp/small_zipformer_ru/metrics.json`).
Коэффициент мобилы 5–10× (меньше кэш, ниже частоты, нет AVX):

```
RTF_mobile = 0.018949 × (5…10) = 0.095…0.189
t_ASR(60 с) = 60 × RTF = 5.7…11.4 с
```

**Оценка: RTF 0.095–0.19; 5.7–11.4 с на 1 мин аудио.**

### 4.5 Диаризация на телефоне

Desktop baseline: sherpa-onnx pyannote segmentation + CAM++ + FastClustering,
1 thread CPU, RTF **0.0775** (`reports/diar_engineer/run_A.json`).
Коэффициент 5–10×:

```
RTF_mobile = 0.0775 × (5…10) = 0.388…0.775
t_diar(60 с) = 23.3…46.5 с
```

**Оценка: RTF 0.39–0.78; 23–47 с на 1 мин аудио.** Диаризация — второе
по тяжести звено после LLM.

### 4.6 VAD

Отдельного замера VAD в проекте нет. Для energy/webrtc-подобного VAD
принимаем **0.2–0.5 с на 1 мин аудио** (оценка, не замер).

### 4.7 Суммарный пайплайн на 1 мин аудио

| Стадия | Оценка, с/мин | Статус |
|---|---:|---|
| VAD | 0.2–0.5 | оценка |
| ASR (small zipformer int8) | 5.7–11.4 | оценка (desktop RTF × 5–10) |
| Диаризация | 23.3–46.5 | оценка (desktop RTF × 5–10) |
| LLM `punctuate` | 24–64 (среднее 38) | оценка (bandwidth-bound) |
| **Итого (punctuate)** | **53–122, среднее ~82** | **оценка** |
| **Итого (full)** | **79–118, среднее ~99** | **оценка** |

То есть полный пайплайн на среднем телефоне — **RTF ≈ 0.9–2.0** (оценка),
без запаса на real-time. Основные вклады: диаризация и LLM. Для RTF ≤ 0.5
нужны: более лёгкая диаризация (или отказ от неё в пользу 2–3 спикеров),
квантование LLM до int4 с оптимизированным ядром, батчинг сегментов и
сокращение числа LLM-вызовов (постпроцесс по абзацу, а не по сегменту).

### 4.8 Пик RAM пайплайна

| Компонент | Оценка, МБ |
|---|---:|
| LLM int4 (веса + KV 512 + буферы) | 1300–1500 |
| ASR small zipformer int8 (модель + runtime) | 150–250 |
| Диаризация (segmentation + embedding + runtime) | 120–200 |
| VAD + приложение/аудио | 100–200 |
| **Пик при последовательной загрузке** | **~1500–1800** |
| **Пик при одновременной загрузке** | **~1700–2100** |

Для бюджета Т3 (не задан) это ориентир: LLM доминирует, поэтому модели
ASR/диаризации нужно выгружать до LLM-стадии или держать в одном процессе
с осторожным управлением памятью.

## 5. Верификация ONNX int4 против torch bf16

10 предложений `punct_eval`, режим `punctuate`, greedy.

| Метрика | torch bf16 (CUDA) | ONNX int4 (CPU) |
|---|---:|---:|
| Точное совпадение текста | — | 3/10 |
| Средняя char-similarity | — | **0.9856** |
| Punct micro F1 | 0.761905 | 0.681818 |
| Boundary F1 | 0.833333 | 0.720000 |
| Сек/элемент | 1.079 (300) | 1.515 (10) |

Вывод: int4-комплект воспроизводит суть вывода torch-версии (98.6 %
посимвольного совпадения), но теряет ~0.08 punct F1. Для Android-рантайма
комплект валиден; для максимального качества пунктуации — int8 или
пост-обработка правил.

## 6. Ограничения

- **Домен пунктуации**: Tatoeba — письменные бытовые предложения, не
  спонтанная речь и не телефонный канал; пунктуация авторская.
- **Correction-набор**: 13 пар, 497 слов; доля improved/worsened
  статистически грубая (шаг 1/13). Ошибки ASR синтетические (взяты из
  baseline-гипотез), а не размеченные вручную.
- **Full-режим**: модель склонна перефразировать и галлюцинировать;
  WER растёт, false-alarm 16 %. Это свойство модели/промпта, а не ошибка
  метрики.
- **Мобильные цифры — оценки**, не замеры: нет реального телефона;
  коэффициенты 5–10× и bandwidth-bound модель — допущения.
- **ONNX-бэкенд CPU-only** в текущем venv; GPU-замеры сделаны на torch,
  не на ONNX Runtime GenAI.
- **Пик RAM** — оценка по размерам весов/KV/буферов; реальный RSS Android
  зависит от рантайма, NNAPI/XNNPACK и фрагментации.
- **Лицензия датасета GrandMaster2** не проверялась; для Apache-2.0 весов
  это не блокер, но должно быть закрыто лицензионным аудитом.
