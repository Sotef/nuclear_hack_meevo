# Ключевые решения

Каждое решение принято по цифрам, полученным на одном тестовом наборе
(`artifacts/data/test`, 13 записей, 5.2 мин) и реальном устройстве
(Samsung SM-N9750, Snapdragon 855, Android 12). Отчёты экспериментов —
в `artifacts/test-results/reports/`.

## 1. ASR: GigaAM v3 RNN-T вместо small-zipformer-ru

| | WER micro | Размер | RTF CPU | Чанк |
|---|---:|---:|---:|---|
| small-zipformer-ru int8 | 0.147 | 25.7 MiB | 0.018 | 19 с |
| **GigaAM v3 int8** | **0.121** (−18%) | 221 MiB | 0.088 | 60 с |

Решение: качество перевесило ×8.6 по размеру; RTF 0.09 всё равно далёк от
предела. Лицензия GigaAM v3 — MIT (подтверждена по metadata энкодера `version=3`;
внимание: GigaAM v2 в экосистеме sherpa — NC, запрещена). Компактный zipformer
сохранён как альтернатива (его WER 0.147 — baseline проекта).

## 2. Пунктуация: RUPunct (т9) вместо LLM

| | Punct F1 | Boundary F1 | Скорость | Размер |
|---|---:|---:|---:|---:|
| без пунктуации | 0.0 | 0.0 | — | — |
| LLM QVikhr int4 | 0.757 | 0.849 | ~2.5 с/сегмент | 1.1 GiB |
| **RUPunct-small int8** | **0.838** | **0.948** | **2 мс/сегмент** | 28 MiB |

Специализированная модель лучше LLM и на 3 порядка быстрее. LLM освобождён
для смысловых задач. Отклонённые альтернативы: китайский CT-Transformer
(на русском F1 = 0, склеивает слова), Horizon-Labs truecase (запасной).

## 3. LLM: QVikhr-3-1.7B int4

- Gamayun 1.5B — **отклонён**: нет публичных весов и лицензии (только статья).
- MiniCPM5-2B (+LoRA на T-Wix, smoke 10k): punct F1 **0.782** — лучший, но
  токенизатор падает в ONNX Runtime GenAI (SIGABRT Scudo в JNI
  `tokenizerApplyChatTemplate`); на устройстве не запустился. Адаптер сохранён
  (`artifacts/models/llm_minicpm5/smoke/`), при починке токенизатора — верный кандидат.
- **QVikhr-3-1.7B int4** (Apache-2.0): работает на устройстве (15–16 ток/с),
  F1 0.757. Выбран для LLM-анализа (конспект/главы/склейка).
- Штрафы `repetition_penalty`/`no_repeat_ngram_size` **убраны**: они заставляли
  модель заменять повторяющиеся слова синонимами («все…все» → «поспело»).
  Корневая причина «одна фраза ×30 раз» — сырой промпт без chat-шаблона; решено
  ручным рендером Qwen3-ChatML (JNI-баг applyChatTemplate).

## 4. Диаризация: глобальная, не по чанкам

pyannote segmentation-3.0 + CAM++ + FastClustering (thr 0.7) — на всю запись
целиком. Початковая диаризация (как в решениях-аналогах) даёт локальные ID
(`speaker_1` разных чанков — разные люди), что ломает диалог. Наши ID стабильны;
FA 0/10 на односпикеровых записях. Входная модель починена (model.fixed.onnx,
топологическая сортировка для ORT 1.22+).

## 5. Склейка разрезанных фраз — LLM предлагает, код решает

LLM возвращает пары номеров строк, слияние выполняется детерминированно
(текст конкатенируется, спикер — от более длинной части). Кросс-спикерные
склейки помечаются `doubtful`. LLM никогда не переписывает текст на этом шаге.

## 6. Формат вывода: единый JSON-контракт v0.2

`segments` с `text`/`text_raw`/`edits`/`doubtful`, `summary`, `chapters` —
additive-поля, обратно совместимы. Схема команды (транскрипт вида
`{speaker_id,start_ms,end_ms,text}`) поддерживается как альтернативный экспорт.

## 7. Интерфейс: одна кнопка и реальные прогрессбары

Убраны разрозненные кнопки (конспект/главы/экспорт-форматы и т.п.): один запуск
«Обработать всё», этапы с галочками и **живым ETA** (пересчёт по темпу стадии,
оценка до старта — по замерам на устройстве). Три оформления A/B/C по дизайн-макетам.

## 8. APK распространяется через GitHub Releases

GitHub блокирует файлы >100 МБ в git-истории (`pre-receive hook declined`);
APK (1.4 ГБ) выкладывается релиз-ассетом, в git остаётся код и манифесты моделей.

## 9. Тонкая настройка LLM на T-Wix — с оговоркой

LoRA smoke (10k строк T-Wix, 2500 шагов, RTX 3080, 1.8 ч) поднял punct F1
MiniCPM5 с 0.441 до 0.782, но режим правок слов (`correct`) слегка ухудшает WER
(+0.010) — полный прогон (499k строк) признан нецелесообразным по времени (~89 ч)
и не запускался. Решение: для пунктуации — RUPunct (решение №2), T-Wix-адаптер
оставлен как исследовательский артефакт.
